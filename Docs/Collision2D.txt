#ifndef GAME_RIGIDBODY2D_HPP
#define GAME_RIGIDBODY2D_HPP

#include "Vector2D.hpp"

/**
 * @file RigidBody2D.hpp
 * @brief Point-mass motion state and its time integration.
 *
 * Holds position, velocity and acceleration in continuous world space and
 * advances them with SEMI-IMPLICIT (symplectic) EULER, which is stable for
 * interactive simulation:
 *
 *      velocity += acceleration * dt;
 *      position += velocity     * dt;   // uses the just-updated velocity
 *
 * The simulation uses a fixed timestep, so integrate() is called with the same
 * dt throughout a run, keeping motion reproducible.
 */
struct RigidBody2D {
    Vector2D position;      ///< World position, in pixels.
    Vector2D velocity;      ///< Pixels per second.
    Vector2D acceleration;  ///< Pixels per second squared.

    /**
     * @brief Advances the body by one fixed step (semi-implicit Euler).
     * @param dt Timestep in seconds.
     * @pre dt > 0.
     */
    void integrate(float dt) noexcept;
};

#endif // GAME_RIGIDBODY2D_HPP

## Implementation Notes

### Why the order of the two lines is load-bearing

| Method | Step 1 | Step 2 | Energy behaviour |
|---|---|---|---|
| **Explicit (forward) Euler** | `velocity += accel * dt` | `position += old_velocity * dt` | Pumps energy into the system → unstable spiral |
| **Semi-implicit (symplectic) Euler** ✓ | `velocity += accel * dt` | `position += **new**_velocity * dt` | Conserves energy → stable orbits and springs |
| Implicit (backward) Euler | requires solving a linear system | — | Dissipates energy → overdamped |

Swapping the two lines here would silently revert to explicit Euler — the simulation would compile and run, but gradually explode under sustained forces (e.g., gravity + bounce).

### Why `noexcept` is kept despite the `assert`

`assert` aborts via `std::abort()`, which does not throw. `noexcept` is therefore correct: the contract violation terminates the process rather than unwinding the stack. In release builds (`-DNDEBUG`) the assert vanishes entirely, making `integrate` a trivial two-line hot path with no overhead.

## Test Design Notes

### Test 2 — The Integration Proof (Most Critical)

This test is designed to **mathematically falsify explicit Euler** if it were accidentally implemented instead. With `pos=(0,0)`, `vel=(0,0)`, `accel=(2,3)`:

| Method | `pos.x` after 1 step | Passes? |
|---|---|---|
| **Semi-implicit (symplectic) Euler** ✓ | `0 + (0 + 2×0.5) × 0.5` = **0.5** | ✅ |
| Explicit (forward) Euler ✗ | `0 + 0 × 0.5` = **0.0** | ❌ |

Starting from rest is the essential setup — it makes `vel_old = (0,0)`, so the two methods produce **different position results** from the very first frame. Any other initial velocity would mask the bug.

### Test 3 — Frame-by-Frame Gravity Table

The expected values are computed purely by hand to avoid circular reasoning (not derived from the code being tested):

| Frame | `vel.y` | `pos.y` |
|---|---|---|
| 0 (start) | 0 | 0 |
| 1 | 10 | 1 |
| 2 | 20 | 3 |
| 3 | 30 | 6 |

The quadratic growth in `pos.y` (1 → 3 → 6, differences +2, +3) is the characteristic signature of semi-implicit Euler with constant acceleration — a quick sanity check that energy is accumulating correctly across frames.
